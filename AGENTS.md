# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## What this is

Pen runs AI programming agents (Claude Code, Codex, OpenCode, Pi) in a Docker container scoped to one project directory, with egress limited to a domain allowlist and owner-scoped GitHub credentials. The host CLI is a .NET 11 Native AOT binary (`cli/Pen`); the container side is `compose.yaml`, `image/` (Dockerfile + entrypoint), `proxy/` (squid + default allowlist) and `templates/` (first-run user config and home seed). See README.md for an introduction and installation, docs/usage.md for detailed user-facing behavior, docs/limitations.md for what Pen doesn't protect against, and CONTRIBUTING.md for the build/test/release workflow.

## Commands

Full details in CONTRIBUTING.md. The essentials (.NET commands run from `cli/`; SDK pinned in `cli/global.json`, xunit v3 on Microsoft.Testing.Platform):

```
cd cli && dotnet build         # warnings are errors
cd cli && dotnet test          # unit tests; --filter-class Pen.Tests.CliTests / --filter-method "*Name*"
cli/install.sh                 # AOT-publish and install ~/.local/bin/pen
tests/smoke.sh                 # end-to-end checks against the *installed* pen; needs Docker
SMOKE_ONLY="7 13" tests/smoke.sh   # only those sections (the fixture setup always runs)
```

## Architecture

**Embedded resources.** `Pen.csproj` embeds `compose.yaml`, `image/**`, `proxy/**`, `templates/**`, `tools/**` under their repo-relative paths (`Embedded.cs`). The installed binary never reads this repo, so **changes to any of those files only take effect after rebuilding/reinstalling the CLI**. Every installation, including planned Homebrew packages and release binaries, builds `pen:latest` locally from the embedded Dockerfile and supporting files; Pen does not publish its own container image. `Embedded.ImageHash()` hashes `image/`; `Image.EnsureCurrent()` rebuilds `pen:latest` when the label doesn't match, so editing `image/` triggers a rebuild on next session. `pen upgrade` rebuilds locally, always with a new base ID (`PEN_REFRESH`), so agents and tools reinstall.

**Flow** (`Program.cs`): `Cli.Parse` → `Config.EnsureUserConfig` (creates `~/.config/pen/` from `templates/`) → `Project.Resolve` (cwd real path; key `pen-<dir>-<hash>` of the main checkout (`RepoDir`) names volumes, project image and runtime dir, so a repo's linked worktrees share it while `Dir`/`PROJECT_DIR` stays the worktree) → command (`Session`, `AllowCommand`, `Trust`, `Sign`, `Reset`; `Ps` and `Prune` run before `Config`/`Project`: `Ps` lists `Sessions.RunningEverywhere`, `Prune` classifies every key with volumes or a runtime dir by its `project-dir` as live, moved, missing or unknown and removes moved/missing ones under `project.lock` exclusive, plus `pen-tools` images on an old base). User-facing errors are `PenException` (message + exit code).

**Sessions** (`Session.cs`, `SessionDir.cs`, `SessionSignals.cs`): each session is its own compose project `<key>-<id>` with a dir under the project's runtime dir holding the generated `compose.yaml`, `session.yaml` override (`SessionCompose.Override`: mounts, dind settings, the ports service), `squid.conf`, `allowlist.txt`, `session.env`, `command`/`started`/`ports`/`tools` (for `pen ps`), `tool-domains`, lock and `proxy.log`. Presence of `compose.yaml` marks a session open. Every command that resolves a project writes the main checkout's real path to the runtime dir's `project-dir` (`Session.EnsureRuntimeDir`), which `pen prune` uses to tell moved or deleted projects apart. Locking (`Sessions.TakeFor*`): sessions hold `project.lock` and their dir's `worktree-<hash(dir)>.lock` shared; `reset` takes `project.lock` exclusive; `sign` takes `project.lock` shared and the worktree lock exclusive, so it's refused only by sessions in its own dir; a dind lock allows one `--docker` session per project. Sessions whose Pen died are cleaned up by the next run (`FinishDeadSessions`). Teardown must remove the agent and dind, or establish their absence with a successful daemon query, before checking Git. If this fails, the session files are retained and the command fails for retry. Signals: SIGINT/SIGQUIT go to the agent; SIGHUP/SIGTERM trigger the normal end path (`SessionSignals`). Volumes (`_home`, `_nuget`, `_dind`) are external and shared by all sessions of a project.

**Isolation**: the agent is on an `internal` network; only the squid proxy has egress. Forwarded ports (`--port`, `ports`) add a `ports` service (pen:latest running socat as `nobody`, no caps, read-only root) on `sandbox` plus a non-internal `ports` network, publishing `127.0.0.1:<p>:<p>` and relaying to the agent by container name (`compose run` gives it no service alias); `Port.Choose` checks each port on the host first (a taken `--port` is an error, a taken config port a warning; never remapped). `pen allow` rewrites the allowlists of running sessions started in its dir (all projects' with `--global`) live. The entrypoint (`image/entrypoint.sh`) runs twice: as root with minimal caps to create the user from `PEN_UID/PEN_GID`, then as the agent with all caps dropped; it copies the home seed (`~/.config/pen/home`, mounted read-only) into `$HOME`. Under rootless Docker the agent is UID 0 with no capabilities on a read-only root fs (`Docker.IsRootless`).

**Protecting the host's git** (`RepoGuard`, `RepoScan`, `GitCheck`, `GitConfigFile`, `ProtectedFiles`, `PausedGit`, `HooksPath`): this is best-effort, and `.git` is untrusted while a session runs, so the docs tell users to keep host and IDE git out of the repo until Pen exits, including `pen sign` in another worktree (it's refused only in its own dir); `.git/commondir`, for one, can't be mounted in advance. With `--docker` the agent can undo the mounts through the privileged daemon: config is still restored at the end, but nothing checks hooks. Pen refuses nested repos (including a submodule with its own `.git` dir: the refusal suggests `git submodule absorbgitdirs`), symlinked `.git`, `commondir`, `.git` files that aren't validated linked worktrees (`RepoScan.ResolveWorktree`) or checkouts of known submodule repos (`RepoScan.ResolveModuleCheckout`: `gitdir:` names one, whose `core.worktree` points back), and worktrees of bare repos. In a linked worktree, the main repo's git dir (`CommonGitDir`) is mounted read-write with the same protections, plus the gitfile and the main checkout's `HEAD`/`index` read-only; the session saves the common dir (`started-with-git`) for the end check. It mounts `.git/config`, `.git/hooks`, `.pen/` and worktrees' `commondir` read-only over themselves (via `session.yaml`; `ProtectGitDir`), and the `.git/worktrees/<n>` entry of each worktree outside the project read-only as a whole (it looks dangling in the sandbox); each submodule repo in the git dir (`modules/**`, `worktrees/*/modules/**`, recursively; `RepoScan.FindModuleRepos`) gets the same `ProtectGitDir` mounts, as does each dir between the git dir and it (so none can be moved aside and a forged repo put in its place), and one that's a symlink or has a `commondir` is refused; and checks `.git` at session end before running any host git. Recursive includes from config and config.worktree are protected, including worktreeConfig enabled through includes; conditional includes are followed conservatively. Writable symlink paths for includes are refused. The session saves the module repos there at start (`modules`); the end check quarantines any others (and repos nested in them, and a `commondir` in a kept one), and only the kept ones' checkouts are the project's own. `pen sign` keeps the ones there now. An entry whose name isn't valid UTF-8 can't be looked inside (`Native.ListUndecodable`): a directory, symlink or unknown type in the tree, or anything in `modules`/`worktrees`, is refused at start and is "couldn't check" at the end. The single-file mounts (except a linked worktree's `HEAD`/`index`) are `Mount.Verify`: `ProtectedFiles` saves them to `protected/` in the session dir with a manifest, refusing a file that isn't regular or is over 1 MB, and a session started alongside another takes that one's copies as its baseline. First in the session-end check, it compares them byte for byte: a changed file is copied to `….pen-quarantine` and written back in place (another session's mount pins the inode), anything else there is renamed aside and the file recreated. If that can't complete, the session's files stay (the session stays open, so the next session start, `pen sign` or `pen reset` retries, and new sessions are refused until it works; `GitCheck.KeptCopiesAdvice` prints the way out); once it does, the copies are deleted and the manifest stays as `restored-manifest.json` until the session's files go. The end check also quarantines any `config.worktree` in the git dir, its worktree entries and module repos that the manifest doesn't vouch for (`ProtectedManifest.Vouches`, a pass in `PausedGit.PromptHazards`): one saved at the start, or in a directory that session had read-only. One first seen while another session's agent could have written there, or inherited from a session that adopted it, is `Adopted`: never vouched for, even unchanged. `pen sign` skips this. The same check warns about paused operations (`PausedGit.Find`, also in `pen sign`), which stay in place since they may be the user's, and quarantines what `git-prompt.sh` would expand at the next prompt (`PausedGit.PromptHazards`: `msgnum`, `end`, `next`, `last`, `head-name` holding what git wouldn't write). If the check can't finish it's a `Failure`: `GitCheck.NotCheckedWarning` prints, teardown continues and Pen runs no host git there. At session start, `RepoGuard.WarnIfCaseMayFold` warns if a probe in the common git dir finds it case-insensitive (`.git/CONFIG` gets past a single-file mount), and `HooksPath` warns if the main repo's `core.hooksPath` (not a submodule's) leads anywhere the sandbox can write other than `.git/hooks`; both warn on every session and block nothing. `HostGit` gives Pen's own git calls overrides that turn off hooks, `core.fsmonitor` and the pager. `RepoGuard` reads files directly and never runs git — keep it that way, since the agent may have planted git config/hooks.

**GitHub**: supply a read-only fine-grained PAT per owner from `[github]` in user `config.toml`, chosen by `origin` owner (`GitHub.cs`). Pen passes credentials through without checking or reducing their permissions; write-capable credentials allow GitHub writes. `pen sign` (`Sign.cs`) re-creates unpushed commits on the host with the user's signature. Only `%G?` of `G`, read with verification settings from the global config (`Sign.VerificationConfig`), counts as signed, so a header or a repo's own settings can't fake it; `Sign.VerificationHint` explains when what it just signed doesn't verify, which makes each run re-sign.

**Config** (`Config.cs`): `~/.config/pen/` and a project's `.pen/` each hold a `config.toml` (TOML via Tomlyn). Parsing validates the TOML syntax tree first (`SyntaxParser.Parse(…, validate: true)`, errors with line numbers), then reads the untyped `TomlTable` through the source-generated `TomlContext` (never reflection-based `TomlSerializer` overloads: AOT) and applies Pen's own key checks. User `config.toml` (secrets allowed): `allow`, `tools`, `[github]` tokens per owner, `[env]`. Project `.pen/config.toml`: `allow`, `tools`, `github_owner`, `docker`, `ports` (merged with `--port` by `Port.Merge`, each remembering whether the flag asked for it) — no secrets. Keys belong to one file or the other, except `allow` and `tools`, whose lists are appended (`allow`: defaults, user, project; `tools`: user, project, `--tool`); if another key ever becomes valid in both, the convention is project scalars override and lists append. `.pen/` is agent-writable input, so `Trust` gates it: new `allow` domains, project `tools`, `docker = true`, a `github_owner` differing from `origin`, and a hash of `.pen/` except `config.toml` when there's a Dockerfile (`PenDirHash`: hostile content means no hash) must be approved in `TrustStore` (`<runtime dir>/trust-<hash(dir)>`, per directory, strict lines, corrupt means nothing approved) before a session uses them, `pen upgrade` builds or `pen allow` applies them live; `Image.EnsureProjectLayer` builds only from a private copy under the runtime dir (`LayerContext`), without `config.toml`, whose own hash must be the approved one, so a later change to `.pen/` can't reach the build; prompts likewise show and approve a retained copy (`LayerContext.Review`). `pen allow` edits the `allow` array in place (`ConfigEdit`: insertions at syntax-tree offsets, then a re-parse that must show only the new domains added, written via temp file + rename keeping the mode). A pre-TOML `config` file in either dir is an error, not silently ignored. An optional `.pen/Dockerfile` builds a per-project image `FROM pen:latest`, tagged `<key>:latest` in the main checkout and `<key>-<hash(dir)>:latest` in a linked worktree (`Image.ProjectLayerName`).

**Tools** (`Tools.cs`, `Recipes.cs`): `tools` and `--tool` take `name` or `name:version`. `ToolSpec.TryParse` resolves the recipe's default and keeps a version exactly as written (`24.04` and `24.4` are different; a recipe's regex rejects forms it doesn't want); `ToolSpec.TryCanonicalize` drops exact duplicates and sorts ordinally, and that list is the tools' identity, so order never matters. Project `tools` are agent-writable, so a version must pass a fixed character check as well as matching all of the recipe's regex before it's used. A recipe is exactly `tools/<name>/tool.toml` and `install.sh` (`RecipeCatalog`); `hidden = true` keeps one out of `pen --tool list` and messages, as for `pen-test`, Pen's own test recipe. `kind = "agent"` marks an agent recipe (`Recipe.IsAgent`, listed apart from tools): a command whose first word is a visible agent's name implies `name:default` (`ToolSpec.ImpliedAgent`) unless user, project or `--tool` already names that agent; `Session.Run` adds it to the `--tool` list, so it needs no approval. The base has no agents: agent recipes (`claude`, `codex`, `opencode`, `pi`) install with the base's private Node (`/opt/pen/node`, not on `PATH`, which recipes may use) into `/opt/pen/<agent>` and link or wrap the command into `/usr/local/bin` (Codex and Pi run on that Node; `codex` also writes `/etc/codex/managed_config.toml`), and bring their providers' domains, which aren't defaults. `PEN_REFRESH` is the base's last layer: `pen upgrade` sets it to the time, so the base always gets a new ID and every tools image, agents included, rebuilds on next use (a normal build leaves it at `0`, so it's cached). `ToolsImage` builds `pen-tools:<hash>` from a generated Dockerfile and tar context, reusing an existing tag; the hash covers the `pen:latest` ID, the canonical list, the recipes' files and the Dockerfile, never the project. Each recipe gets one exec-form `RUN` with only its own directory mounted. A recipe's `[env]` is `ENV` after the `RUN`s, so a `.pen/Dockerfile` and the user's `[env]` can override it. A session's tools are user config, project config and `--tool`: `ToolSpec.Merge` happens before the trust check, then `ToolsImage.Ensure` and `Image.EnsureProjectLayer` give the image to run, and recipes' domains join the allowlist. The session dir's `tools` (for `pen ps`) and `tool-domains` record them, so `AllowCommand.Apply` keeps exactly what the session started with and never reads tools from `.pen/` live. Project `tools` are approved as `name:version` together with the domains shown (`Trust.UnapprovedTools`, store lines `tool` and `tool-allow`, kept apart from `allow` approvals in both directions), so a domain a recipe adds later asks again and a removed one doesn't. An entry the user also names doesn't ask, and isn't approved by that. `pen upgrade` rebuilds user tools and approved project tools. `pen prune` removes `pen-tools:<hash>` images whose `pen.base-id` isn't the current base, selecting by repository since stacked layers inherit the label.

**Home seed** (`image/sync-seed.sh`): seed-managed files overwrite sandbox copies on every start regardless of mtime. Files absent from the seed remain in the home volume; removing a seed file stops managing it without deleting the sandbox copy. Known credential paths and `.docker/` are excluded. Claude's mixed `.claude.json` takes only the seed's entire `mcpServers` map, preserving every other local field. `image/docker-proxy.sh` configures session proxy settings separately. See docs/usage.md for the ownership inventory.

## Conventions

- Verifying a change: after each change, build, unit tests and the smoke sections it touches (`SMOKE_ONLY`); the full smoke suite before finishing a larger piece of work.

- Code must stay AOT/trim-safe (`PublishAot`, `IsAotCompatible`): no reflection-based JSON serialization etc. Native calls live in `Native.cs`.
- Tests access internals via `InternalsVisibleTo`; use the `TempDir` and `Git` helpers in `Pen.Tests`.
- Keep architecture comments tied to current invariants or documentation, rather than the removed historical architecture plan.
- Naming: the project is "Pen" in prose, docs and comments; the command stays `pen` (also `pen sign`, `pen:latest`, `.pen/`, `PEN_*`).
- Markdown: don't hard-wrap prose. Each paragraph and list item is one line, left to the editor's soft wrap; line breaks only where they change the rendering (code blocks, tables, list items, headings).
