# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## What this is

Pen runs AI programming agents (Claude Code, Codex, OpenCode, Pi) in a Docker container scoped to one project directory, with egress limited to a domain allowlist and owner-scoped GitHub credentials. The host CLI is a .NET 11 Native AOT binary (`cli/Pen`); the container side is `compose.yaml`, `image/` (Dockerfile + entrypoint), `proxy/` (squid + default allowlist) and `templates/` (first-run user config and home seed). See README.md for an introduction and installation, docs/usage.md for detailed user-facing behavior, docs/limitations.md for what Pen doesn't protect against, and CONTRIBUTING.md for the build/test/release workflow.

## Commands

Full details in CONTRIBUTING.md. The essentials (.NET commands run from `cli/`; SDK pinned in `cli/global.json`, xunit v3 on Microsoft.Testing.Platform):

```
cd cli && dotnet build         # warnings are errors
cd cli && dotnet test          # unit tests; --filter-class Pen.Tests.CliTests / --filter-method "*Name*"
cli/install.sh                 # AOT-publish and install ~/.local/bin/pen
cd cli && dotnet run --project Pen.SmokeTests   # end-to-end checks against the *installed* pen; needs Docker
cd cli && dotnet run --project Pen.SmokeTests -- --filter-class "*CliDispatchTests"   # one class (--filter-method too)
```

## Architecture

**Layout.** Each namespace is a folder under `cli/Pen/`, one main type per file (small records and enums used with it may live alongside it): `Pen` (`Program`, the entry and command dispatch, and `PenException`), `CommandLine` (`CommandParser`, `CommandTree`, `CommandBoundary`, `Command`, `ShellGlob`), `Commands` (one sealed `…Command` per subcommand other than run, which is `Session` in `Sessions`; `EgressTarget` and `EgressMessages` are what `AllowCommand` and `DenyCommand` share), `Configuration` (`UserConfiguration`, `ProjectConfiguration`, `ConfigParser`, `ConfigLoader`, `UserConfigInitializer`, `TomlReader`, `ConfigEdit`, `ConfigFileEditor`, `Seed`, `GitHub`, `TomlContext`, `ProjectDetection`, `ProjectTemplate`), `Projects` (`Project`, `ProjectContext`, `ProjectRuntime`, `StartDir`), `Platform` (`Native`, `Proc`, `Docker`, `FileLock`, `Out`, `HostEnv`, `Answers`, `Retry`, `PathChecks`, `Embedded`), `Sessions` (`Session`, `InitHint`, `InteractiveShell`, `SessionDir`, `SessionRegistry`, `SessionSignals`, `SessionCompose`, `ComposeClient`, `Port`), `Proxy` (`Allowlist`, `EgressPolicyResolver`, `BlockedDomainQuery`, `SessionAclUpdater`, `ProxyLogTrimmer`), `Trust` (`TrustGate`, `TrustStore`, the trust requests, `PenDirHash`, `LayerContext`), `Tools` (`ToolSpec`, `Recipe`, `RecipeCatalog`), `Images` (`Image`, `ToolsImage`), `GitProtection` (the host-git protection at session start and end), `Masking` (`HidePattern`, `MaskPlanner`, `MaskPlan`, `MaskFiles`, `MaskMessages`: files hidden or replaced in the sandbox) and `Signing` (`pen sign`'s machinery and Pen's own host git calls: `HostGit`, `BranchSigner`, the commit reading, verifying and rewriting).

**Embedded resources.** `Pen.csproj` embeds `compose.yaml`, `image/**`, `proxy/**`, `templates/**`, `tools/**` under their repo-relative paths (`Embedded.cs`). The installed binary never reads this repo, so **changes to any of those files only take effect after rebuilding/reinstalling the CLI**. Every installation, including planned Homebrew packages and release binaries, builds `pen:latest` locally from the embedded Dockerfile and supporting files; Pen does not publish its own container image. `Embedded.ComputeImageHash()` hashes `image/`; `Image.EnsureCurrent()` rebuilds `pen:latest` when the label doesn't match, so editing `image/` triggers a rebuild on next session. `pen upgrade` (`UpgradeCommand`) rebuilds locally, always with a new base ID (`PEN_REFRESH`), so agents and tools reinstall.

**Flow** (`Program.cs`): `CommandParser.Parse` (System.CommandLine over the tree in `CommandTree`, no response files or directives, bundling off; `CommandBoundary` first inserts a `--` before the command's first token so everything from it on passes through unchanged; Pen itself refuses unknown options before the command, since System.CommandLine turns them into command words; help and version are `Builtin`, run through the parse result) → `UserConfigInitializer.EnsureExists` (creates `~/.config/pen/` from `templates/`) and `ConfigLoader.LoadUser` → `Project.Resolve` (cwd real path; key `pen-<dir>-<hash>` of the main checkout (`RepoDir`) names volumes, project image and runtime dir, so a repo's linked worktrees share it while `Dir`/`PROJECT_DIR` stays the worktree) → command (`Session`, `InitCommand`, `AllowCommand`, `DenyCommand`, `TrustCommand`, `SignCommand`, `CleanCommand`; `PsCommand` and `CleanStaleCommand` (`pen clean --stale`) run before `UserConfigInitializer.EnsureExists`, `ConfigLoader.LoadUser` and `Project.Resolve`: `PsCommand` lists `SessionRegistry.FindRunningEverywhere`, `CleanStaleCommand` classifies every key with volumes or a runtime dir by its `project-dir` as live, moved, missing or unknown and removes moved/missing ones under `project.lock` exclusive, plus `pen-tools` images on an old base). User-facing errors are `PenException` (message + exit code).

**Sessions** (`Session.cs`, `SessionDir.cs`, `SessionSignals.cs`): each session is its own compose project `<key>-<id>` with a dir under the project's runtime dir holding the generated `compose.yaml`, `session.yaml` override (`SessionCompose.GenerateOverride`: mounts, dind settings, the ports service), `squid.conf`, `allowlist.txt`, `denylist.txt`, `open-egress.txt`, `session.env`, `command`/`started`/`ports`/`tools` (for `pen ps`), `tool-domains`, `masks/` (the empty file and directory and the replacement copies mounted over hidden and replaced paths), `session.lock`, `acl.lock` (held exclusive by `pen allow`/`pen deny` while they rewrite and reload the ACL files; nothing else takes it, and deleting the session's files deletes it) and `proxy.log`. Presence of `compose.yaml` marks a session open. Every command that resolves a project writes the main checkout's real path to the runtime dir's `project-dir` (`ProjectRuntime.EnsureRuntimeDir`), which `pen clean --stale` uses to tell moved or deleted projects apart. The runtime dir also holds `init-hint`, the marker `InitHint.TryClaim` creates (exclusively) when it shows the `pen init` suggestion, once per project at a session start without `.pen/config.toml`. Locking (`SessionRegistry.TakeFor*`): sessions hold `project.lock` and their dir's `worktree-<hash(dir)>.lock` shared; `pen clean` takes `project.lock` exclusive; `sign` takes `project.lock` shared and the worktree lock exclusive, so it's refused only by sessions in its own dir; a dind lock allows one `--docker` session per project. Sessions whose Pen died are cleaned up by the next run (`Session.FinishDeadSessions`). Teardown must remove the agent and dind, or establish their absence with a successful daemon query, before checking Git. If this fails, the session files are retained and the command fails for retry. Signals: SIGINT/SIGQUIT go to the agent; SIGHUP/SIGTERM trigger the normal end path (`SessionSignals`). Volumes (`_home`, `_nuget`, `_dind`) are external and shared by all sessions of a project.

**Isolation**: the agent is on an `internal` network; only the squid proxy has egress. Forwarded ports (`--port`, `ports`) add a `ports` service (pen:latest running socat as `nobody`, no caps, read-only root) on `sandbox` plus a non-internal `ports` network, publishing `127.0.0.1:<p>:<p>` and relaying to the agent by container name (`compose run` gives it no service alias); `Port.Choose` checks each port on the host first (a taken `--port` is an error, a taken config port a warning; never remapped). `pen allow` and `pen deny` rewrite the ACL files of running sessions started in its dir (all projects' with `--global`; `EgressTarget.ApplyToRunningSessions`, which reports each session's `AclUpdateResult` and goes on past a failure) live. `EgressPolicyResolver` merges the lists (defaults, user `allow`, the project `allow` `TrustGate.SelectAllowedDomains` lets through, tool domains; `deny` from both files), taking the tool domains from each entry point's own source: `ForSessionStart` the session's selected tools, `ForListing` (`pen allow`'s blocked listing, grouped by `BlockedDomainQuery`) the user's and approved project tools, `ForRunningSession` the session's recorded `tool-domains`. The static `proxy/squid.conf` reads three files, written by `Allowlist.RenderFiles` (truncated in place by `SessionAclUpdater` under the session's `acl.lock`, read back through `docker compose exec proxy` until the proxy sees what was written, since a VM's file sharing can lag, and only then `squid -k reconfigure`; a mismatch in any of them skips the reload and fails the command): `denylist.txt` is checked first and beats every allow, `allowlist.txt` holds the named domains, and `open-egress.txt` holds `.` when `allow` has `*` (`Allowlist.AnyDomain`) and is otherwise empty. Raw IPs (`ip_dest`) are always denied, `*` covers names only, and in open mode names that resolve to private ranges (`private_dst`) or not at all (`resolved_dst`) are denied; a domain allowed by name still reaches private addresses, since `allowlist.txt` keeps named domains in open mode (`Allowlist.MergeNamed`). A session without `denylist.txt` predates this, so `*` is never written to it. `pen ps` shows the EGRESS column from `SessionDir.HasOpenEgress`. The entrypoint (`image/entrypoint.sh`) runs twice: as root with minimal caps to create the user from `PEN_UID/PEN_GID`, then as the agent with all caps dropped; it copies the home seed (`~/.config/pen/home`, mounted read-only) into `$HOME`. Under rootless Docker the agent is UID 0 with no capabilities on a read-only root fs (`Docker.IsRootless`).

**Protecting the host's git** (`RepoGuard`, `MountPlanner`, `RepoScan`, `GitDirWalk`, `GitCheck`, `GitQuarantine`, `GitCheckWording`, `GitCheckReport`, `FileModes`, `GitConfigFile`, `GitConfigIncludes`, `ModuleBaseline`, `ProtectedFiles`, `ProtectedFileRestore`, `PausedGit`, `PromptHazardScan`, `HooksPath`): this is best-effort, and `.git` is untrusted while a session runs, so the docs tell users to keep host and IDE git out of the repo until Pen exits, including `pen sign` in another worktree (it's refused only in its own dir); `.git/commondir`, for one, can't be mounted in advance. With `--docker` the agent can undo the mounts through the privileged daemon: config is still restored at the end, but nothing checks hooks. Pen refuses nested repos (including a submodule with its own `.git` dir: the refusal suggests `git submodule absorbgitdirs`), symlinked `.git`, `commondir`, `.git` files that aren't validated linked worktrees (`RepoScan.ResolveWorktree`) or checkouts of known submodule repos (`RepoScan.ResolveModuleCheckout`: `gitdir:` names one, whose `core.worktree` points back), and worktrees of bare repos. In a linked worktree, the main repo's git dir (`CommonGitDir`) is mounted read-write with the same protections, plus the gitfile and the main checkout's `HEAD`/`index` read-only; the session saves the common dir (`started-with-git`) for the end check. It mounts `.git/config`, `.git/hooks`, `.pen/` and worktrees' `commondir` read-only over themselves (via `session.yaml`; `MountPlanner.ProtectGitDir`), and the `.git/worktrees/<n>` entry of each worktree outside the project read-only as a whole (it looks dangling in the sandbox); each submodule repo in the git dir (`modules/**`, `worktrees/*/modules/**`, recursively; `RepoScan.FindModuleRepos`) gets the same `MountPlanner.ProtectGitDir` mounts, as does each dir between the git dir and it (so none can be moved aside and a forged repo put in its place), and one that's a symlink or has a `commondir` is refused; and checks `.git` at session end before running any host git. Recursive includes from config and config.worktree are protected, including worktreeConfig enabled through includes; conditional includes, and the include forms git ignores, are followed conservatively. `GitConfigIncludes` reads each config file once per mount planning or hooksPath check and tags each include as one git reads always, maybe (behind a condition) or never; `MountPlanner` walks it visiting each file once (up to `GitConfigIncludes.MaxFiles` per walk), `HooksPath` replays git's order (repeats re-applied, depth 10, one read budget). Whether an include's path is in the sandbox is decided by identity (`MountPlanner.SpellInSandbox`, by device and inode as in `GitDirLinkCheck`), so a macOS firmlink alias (`/System/Volumes/Data/…`) or another case of the project or git dir counts, and an included file is mounted by its path spelled from there. Writable symlink paths for includes are refused, however the path is spelled (an outside symlink that leads in to one counts: the OS walk reports each symlink the sandbox can repoint), and so is an include, of any form or condition, naming a directory the sandbox can write: git fails on a directory, but the agent could put a config file in its place (a mount doesn't stop that: `.git`, `.git/hooks`, `.pen/` and worktree entries are mounted over themselves, and an include can name them) and make a condition hold; one outside the sandbox is left alone. An include whose path, as the OS walks it, has a `..` after a name the sandbox can replace (a missing or existing directory in the project or git dir, or a symlink there, also when an outside symlink leads in: `MountPlanner.CanBeReplaced`) is refused too: the agent could make that name a symlink, and git would read an unprotected file beside where it leads. The including file's own real directory and those above it are pinned (mount points, or a symlink in their place is renamed aside by `ProtectedFileRestore` before any host git runs), so `../.gitconfig` from `.git/config` and a module repo's `../../x.cfg` stay allowed. The session saves the module repos there at start (`modules`), keeping only those every open session saved too (`ModuleBaseline`, over `SessionRegistry.FindOpen`, so a session whose Pen died counts: read just before the module scan and again before the session dir is written; an open session with no `modules` for this common dir refuses the start), since another session's agent could have made the rest; the end check quarantines any others (and repos nested in them, and a `commondir` in a kept one), and only the kept ones' checkouts are the project's own. `pen sign` keeps the ones there now. The rest of the git dir is walked too, all of it (`RepoScan.ScanGitDir`, at start and in the end check right after the module check, so in `pen sign` too), since git run from a directory in it uses the first repo it finds there, and it can get there through a symlink committed on a branch (it arrives at checkout) or one that leads nowhere until a commit makes `objects/ab`: a `.git` anywhere in it, `.git/.git` included, or a directory git would take for a git dir (`RepoScan.IsGitDirLayout`, as broad as git's `is_git_directory`: a symlinked `HEAD`, `objects`/`refs` of any type) that isn't one of its own (the git dir, the kept module repos and their worktree entries whose `commondir` resolves physically back to them; libgit2 writes it absolute) is refused at start and quarantined at the end. Nothing is skipped, by place or name: object stores and `….pen-quarantine` dirs are walked (a quarantined repo's layout is broken by moving its `HEAD`, so it isn't found again), which costs a little over a second per 50k LFS/annex dirs. A walk doesn't enter a `.git` dir; the end check walks each one it moves aside (`GitCheck.QuarantineFound`). A symlink in the project, of any name (`.git` too), that leads to a directory at or inside the common git dir, or would once a directory it names is made (dangling symlinks met on the way spliced in as the kernel does), or that Pen can't trace (target not UTF-8, a `..` that can't be searched: `NestedScan.UntracedLinks`, worded apart) (`GitDirLinkCheck`: by device and inode up the `..` chain, so a firmlink alias counts) is refused at start and removed at the end (`GitQuarantine.RemoveLink`, via `Native.RemoveSymlink`'s `openat`/`unlinkat` from the project dir without following symlinks; renamed it would lead there still, and the warning prints `ln -s` to recreate it): defence in depth, since the walk finds what it leads to. An entry whose name isn't valid UTF-8 can't be looked inside (`Native.ListUndecodable`): a directory, symlink or unknown type in the tree or the git dir, or anything in `modules`/`worktrees`, is refused at start and is "couldn't check" at the end. The single-file mounts (except a linked worktree's `HEAD`/`index`) are `Mount.Verify`: `ProtectedFiles` saves them to `protected/` in the session dir with a manifest, refusing a file that isn't regular or is over 1 MB, and a session started alongside another takes that one's copies as its baseline. First in the session-end check (`GitCheck`), `ProtectedFileRestore` compares them byte for byte: a changed file is copied to `….pen-quarantine` and written back in place (another session's mount pins the inode), anything else there is renamed aside and the file recreated. If that can't complete, the session's files stay (the session stays open, so the next session start, `pen sign` or `pen clean` retries, and new sessions are refused until it works; `GitCheckWording.KeptCopiesAdvice` prints the way out); once it does, the copies are deleted and the manifest stays as `restored-manifest.json` until the session's files go. The end check also quarantines any `config.worktree` in the git dir, its worktree entries and module repos that the manifest doesn't vouch for (`ProtectedManifest.Vouches`, a pass in `PromptHazardScan`): one saved at the start, or in a directory that session had read-only. A file in a module repo left out of `modules`, a `config.worktree` first seen while another session's agent could have written there, or one inherited from a session that adopted it, is `Adopted`: never written back or vouched for, even unchanged. `pen sign` skips this. The same check warns about paused operations (`PausedGit.Find`, also in `pen sign`), which stay in place since they may be the user's, and quarantines what `git-prompt.sh` would expand at the next prompt (`PromptHazardScan`: `msgnum`, `end`, `next`, `last`, `head-name` holding what git wouldn't write). If the check can't finish it's a `Failure`: `GitCheckWording.NotCheckedWarning` prints, teardown continues and Pen runs no host git there. At session start, `RepoGuard.WarnIfCaseMayFold` warns if a probe in the common git dir finds it case-insensitive (`.git/CONFIG` gets past a single-file mount), and `HooksPath` warns if the main repo's `core.hooksPath` (not a submodule's) leads anywhere the sandbox can write other than `.git/hooks`; both warn on every session and block nothing. `HostGit` gives Pen's own git calls overrides that turn off hooks, `core.fsmonitor` and the pager. `RepoGuard` reads files directly and never runs git — keep it that way, since the agent may have planted git config/hooks.

**Hidden files** (`Masking/`): `hide` (`HidePattern`, in both config files) and `[replace]` (project only) change only what the sandbox sees; host files are never touched and nothing happens at session end. Neither goes through `TrustGate`, since both only narrow what the agent sees, which is why a `[replace]` source that `hide` hides (by pattern or by device/inode) is refused: `.pen/` is agent-writable. `Session.Prepare` runs `MaskPlanner` right after `RepoGuard.EnsureMountTargetsAndPlan`: it walks the project without following symlinks (never into `.git` or the top-level `.pen`), takes literal patterns by a fast path that resolves each segment against the listing, and hides what a matched in-project symlink leads to. Hidden files and directories become read-only mounts of an empty file or directory, replacements of a copy; `Preparation.Masks` (a `MaskPlan`) stays separate from the git-protection mounts, and `MaskPlanner` refuses a mask that equals, holds or is inside one (Docker can't mount there). `[replace]` sources are read through `Native.ReadInsideProject` (`O_NOFOLLOW` at every component, regular files up to 1 MB, hard links refused); `MaxMounts` caps the mounts at 1,000. `MaskPlan.ThrowIfChanged` re-lstats every planned path (device/inode, type, realpath) just before `Session.WriteMasks` (`MaskFiles.Write`) creates `masks/`, and the files are deleted if writing the session dir fails (`WriteSessionDirOrDelete`); the mounts reach `compose` as `Mount.Source` (source differs from target) through `session.yaml`. A change between that check and the container starting can't be caught. `MaskMessages` prints the summary line and warnings (a case probe in `.pen/` via `PathChecks.MayFoldCase`, hard links, `--docker` not enforcing) after the signals are held.

**GitHub**: supply a read-only fine-grained PAT per owner from `[github]` in user `config.toml`, chosen by `origin` owner (`GitHub.cs`). Pen passes credentials through without checking or reducing their permissions; write-capable credentials allow GitHub writes. `pen sign` (`SignCommand`, `BranchSigner`) re-creates unpushed commits on the host with the user's signature (`CommitObject.Parse` parses them, `CommitReader` reads them and checks them against git, `CommitRewriter` re-creates them). Only `%G?` of `G`, read with verification settings from the global config (`SignatureConfig.BuildForVerifying`, used by `SignatureVerifier`), counts as signed, so a header or a repo's own settings can't fake it; `SignatureVerifier.FormatHint` explains when what it just signed doesn't verify, which makes each run re-sign.

**Config** (`UserConfiguration.cs`, `ProjectConfiguration.cs`, `ConfigParser.cs`, `ConfigLoader.cs`): `~/.config/pen/` and a project's `.pen/` each hold a `config.toml` (TOML via Tomlyn). `ConfigLoader.LoadUser`/`LoadProject` refuse a legacy `config` file and read `config.toml` as a regular file of bounded size (`ConfigLoader.ReadText`); `ConfigParser.ParseUser`/`ParseProject` parse it with the recipe catalog passed in, into a `UserConfiguration` or `ProjectConfiguration` (sealed, no setters, each collection its own read-only copy: lists in file order except `tools`, which is canonical, and `[github]` tokens a dictionary keyed ordinally by lowercased owner; `Empty` for a missing file; not records, so no generated `ToString` shows a token or env value; `[replace]` entries are `FileReplacement(Target, Source)`). `ProjectContext` holds both, and code that reads either takes it by its own type, so the user's and the project's settings can't be swapped. `TomlReader.ParseToml`, which tool.toml and detected toolchain files go through too, validates the TOML syntax tree first (`SyntaxParser.Parse(…, validate: true)`, errors with line numbers), then reads the untyped `TomlTable` through the source-generated `TomlContext` (never reflection-based `TomlSerializer` overloads: AOT); `ConfigParser` then applies Pen's own key checks in file order. User `config.toml` (secrets allowed): `allow`, `deny`, `tools`, `hide`, `[github]` tokens per owner, `[env]`. Project `.pen/config.toml`: `allow`, `deny`, `tools`, `hide`, `[replace]`, `github_owner`, `docker`, `ports` (merged with `--port` by `Port.Merge`, each remembering whether the flag asked for it) — no secrets. Keys belong to one file or the other, except `allow`, `deny`, `tools` and `hide`, whose lists are appended (`allow`: defaults, user, project; `deny`: user, project; `tools`: user, project, `--tool`; `hide`: user, project). `[replace]` is project-only. `deny` is valid in both files, never takes `*`, needs no approval (it only narrows access) and is enforced first by squid; `allow` alone accepts the exact entry `*` (`Allowlist.AnyDomain`). A project `*` is its own `TrustGate` approval (`TrustRequest.AnyDomainLine`), and a user `*` covers only a project `*`, never its named domains (`TrustGate.SelectAllowedDomains`); if another key ever becomes valid in both, the convention is project scalars override and lists append. `.pen/` is agent-writable input, so `TrustGate` gates it: new `allow` domains, project `tools`, `docker = true`, a `github_owner` differing from `origin`, and a hash of `.pen/` except `config.toml` when there's a Dockerfile (`PenDirHash`: hostile content means no hash) must be approved in `TrustStore` (`<runtime dir>/trust-<hash(dir)>`, per directory, strict lines, corrupt means nothing approved) before a session uses them, `pen upgrade` builds or `pen allow` applies them live; `Image.EnsureProjectLayer` builds only from a private copy under the runtime dir (`LayerContext`), without `config.toml`, whose own hash must be the approved one, so a later change to `.pen/` can't reach the build; prompts likewise show and approve a retained copy (`LayerContext.TakeForReviewRemovingAbandoned`). `pen allow` edits the `allow` array in place (`ConfigEdit`, pure text: insertions at syntax-tree offsets, then a re-parse that must show only the new domains added, every setting of that file's configuration compared by contents (`ConfigEdit.IsOnlyAdded`); `ConfigFileEditor` reads the file and writes the result via temp file + rename keeping the mode). A pre-TOML `config` file in either dir is an error, not silently ignored. `templates/project/config.toml`, filled by `ProjectTemplate.Render` from `ProjectDetection` (read-only and advisory, three directories deep, only recipe-valid tools and `HidePattern`-valid patterns), is the one template `pen init` (`InitCommand`: never overwrites, approves nothing), `pen allow` and `pen deny` (nothing detected) write. An optional `.pen/Dockerfile` builds a per-project image `FROM pen:latest`, tagged `<key>:latest` in the main checkout and `<key>-<hash(dir)>:latest` in a linked worktree (`Image.GetProjectLayerName`).

**Tools** (`Tools/ToolSpec.cs`, `Tools/Recipe.cs`, `Tools/RecipeCatalog.cs`): `tools` and `--tool` take `name` or `name:version`. `ToolSpec.TryParse` resolves the recipe's default and keeps a version exactly as written (`24.04` and `24.4` are different; a recipe's regex rejects forms it doesn't want); `ToolSpec.TryCanonicalize` drops exact duplicates and sorts ordinally, and that list is the tools' identity, so order never matters. Project `tools` are agent-writable, so a version must pass a fixed character check as well as matching all of the recipe's regex before it's used. A recipe is exactly `tools/<name>/tool.toml` and `install.sh` (`RecipeCatalog`); `hidden = true` keeps one out of `pen tools` and messages, as for `pen-test`, Pen's own test recipe. `kind = "agent"` marks an agent recipe (`Recipe.IsAgent`, listed apart from tools): a command whose first word is a visible agent's name implies `name:default` (`ToolSpec.FindImpliedAgent`) unless user, project or `--tool` already names that agent; `Session.Run` adds it to the `--tool` list, so it needs no approval. The base has no agents: agent recipes (`claude`, `codex`, `opencode`, `pi`) install with the base's Node (`/usr/local`, installed by `image/install-node.sh`: the newest LTS when the base is built, refreshed by `pen upgrade`) into `/opt/pen/<agent>` and link or wrap the command into `/usr/local/bin` (Codex and Pi run through wrappers that `exec /usr/local/bin/node`; `codex` also writes `/etc/codex/managed_config.toml`), and their `tool.toml` brings their providers' domains, which aren't defaults. Each agent's `install.sh` is a few lines that run the base's shared helper for npm agents, `/opt/pen/lib/npm-agent.sh` (`image/npm-agent.sh`, off `PATH`; editing it rebuilds the base and so every tools image), with its package, how the command is exposed, its oldest release and version format. `PEN_REFRESH` is the base's last layer: `pen upgrade` sets it to the time, so the base always gets a new ID and every tools image, agents included, rebuilds on next use (a normal build leaves it at `0`, so it's cached). `ToolsImage` builds `pen-tools:<hash>` from a generated Dockerfile and tar context, reusing an existing tag; the hash covers the `pen:latest` ID, the canonical list, the recipes' files and the Dockerfile, never the project. Each recipe gets one exec-form `RUN` with only its own directory mounted. A recipe's `[env]` is `ENV` after the `RUN`s, so a `.pen/Dockerfile` and the user's `[env]` can override it. A session's tools are user config, project config and `--tool`: `ToolSpec.Merge` happens before the trust check, then `ToolsImage.Ensure` and `Image.EnsureProjectLayer` give the image to run, and recipes' domains join the allowlist. The session dir's `tools` (for `pen ps`) and `tool-domains` record them, so a live update (`SessionAclUpdater.Update`, through `EgressPolicyResolver.ForRunningSession`) keeps exactly what the session started with and never reads tools from `.pen/` live. Project `tools` are approved as `name:version` together with the domains shown (`TrustGate.FindUnapprovedTools`, store lines `tool` and `tool-allow`, kept apart from `allow` approvals in both directions), so a domain a recipe adds later asks again and a removed one doesn't. An entry the user also names doesn't ask, and isn't approved by that. `pen upgrade` rebuilds user tools and approved project tools. `pen clean --stale` removes `pen-tools:<hash>` images whose `pen.base-id` isn't the current base, selecting by repository since stacked layers inherit the label.

**Home seed** (`image/sync-seed.sh`): seed-managed files overwrite sandbox copies on every start regardless of mtime. Files absent from the seed remain in the home volume; removing a seed file stops managing it without deleting the sandbox copy. Known credential paths and `.docker/` are excluded. Claude's mixed `.claude.json` takes only the seed's entire `mcpServers` map, preserving every other local field. `image/docker-proxy.sh` configures session proxy settings separately. See docs/usage.md for the ownership inventory.

## Conventions

- Verifying a change: after each change, build, unit tests and the smoke test classes it touches (`--filter-class`); the full smoke suite before finishing a larger piece of work.

- Code must stay AOT/trim-safe (`PublishAot`, `IsAotCompatible`): no reflection-based JSON serialization etc. Native calls live in `Native.cs`.
- Tests access internals via `InternalsVisibleTo`; use the `TempDir` and `Git` helpers in `Pen.TestSupport`.
- Keep architecture comments tied to current invariants or documentation, rather than the removed historical architecture plan.
- Naming: the project is "Pen" in prose, docs and comments; the command stays `pen` (also `pen sign`, `pen:latest`, `.pen/`, `PEN_*`).
- Markdown: don't hard-wrap prose. Each paragraph and list item is one line, left to the editor's soft wrap; line breaks only where they change the rendering (code blocks, tables, list items, headings).

# C# Engineering Guidelines

## Applying the guidelines in Pen

- Pen is synchronous: only `Proc` waits on tasks (the port probe's connect is bounded by `Socket.Poll`), and there is no `CancellationToken`. Cancellation comes from POSIX signals through `SessionSignals`.
- No interface without a second real production implementation. A test double isn't one.
- `Try…` methods return `bool` and annotate their result with `[NotNullWhen]` or `[MaybeNullWhen]`. Results expose read-only snapshots, not collectors that callers can mutate; CA1002 fails the build on a `List<T>` in any non-private member (private members and private nested types may keep `List<T>`); CA2227 is on but only sees public types, so settable collection properties are kept out by review.
- Banned APIs have one owner each, and everything else goes through it: `DateTime.Now`/`UtcNow`/`Today` (a `TimeProvider` from `Program`), `Thread.Sleep` (`Retry`), `Console` (`Out`; `Program` also writes help and listings and reads stdin, which reaches prompts as `Answers`), `new Process`, `Process.Start`, `StartAndForget` and the `Process.Run…` family (`Proc`), `Environment.GetEnvironmentVariable`, `ExpandEnvironmentVariables` and `CurrentDirectory` (`HostEnv`; the starting directory reaches commands as the `StartDir` `Program` passes on), `Task.Wait`/`WaitAll`/`WaitAny`, `Task<T>.Result`, `ValueTask<T>.Result` and `GetAwaiter().GetResult()` on tasks and value tasks (`Proc`), and `RecipeCatalog.Embedded` (`Program`, which passes the catalog on). The banned-API analyzer (RS0030, `cli/Pen/BannedSymbols.txt`) enforces this in the build; only the owners' files are exempt, in `.editorconfig`.
- Comments: delete documentation that restates a member's name or signature, and `<param>`/`<returns>` on private helpers unless they state a constraint. Keep, as plain complete sentences, every comment that explains intent, an invariant, a security constraint or a platform quirk. Prefer a short summary to a design essay; architecture-level detail belongs here or in `docs/`. Wrap at 120 columns.
- Style: `var` wherever it is legal (explicit types only where `var` can't express them, such as a target-typed collection expression), `is null` and `is not null`, `is T x` patterns instead of `as` plus a null check, collection expressions, target-typed `new`, switch expressions, file-scoped namespaces, no `this.`, and predefined type names. `.editorconfig` enforces most of these in the build for `cli/Pen`; the test projects aren't restyled.

## Core Philosophy

Write modern, idiomatic C# that prioritizes correctness, clarity, maintainability, and simplicity.

- Prefer straightforward, expressive code over clever or overly abstract solutions.
- Write code that is easy to read, reason about, debug, and modify.
- Favor established .NET conventions and standard library capabilities.
- Avoid unnecessary complexity, dependencies, indirection, and boilerplate.
- Use abstractions to solve actual problems, not hypothetical future requirements.
- Optimize for maintainability first, performance where it matters.
- Follow existing project conventions unless there is a compelling reason to improve them.

## Modern C# and Language Features

- Use the latest stable C# features supported by the project's target framework and language version.
- Prefer modern language constructs when they meaningfully improve readability or correctness.
- Use file-scoped namespaces.
- Use collection expressions, pattern matching, switch expressions, target-typed `new`, and other modern syntax where appropriate.
- Prefer `var` when the type is obvious from context; use explicit types when they improve clarity.
- Use records for data with value semantics, not indiscriminately for all classes.
- Use primary constructors when they simplify a type without obscuring its behavior.
- Prefer immutable data where practical, without introducing unnecessary copying or complexity.
- Enable and respect nullable reference types.
- Avoid null-forgiving operators (`!`) unless the invariant is genuinely established.
- Avoid introducing new syntax solely for the sake of appearing modern.

## Code Structure and Design

- Keep classes and methods focused on clear responsibilities.
- Prefer composition over inheritance.
- Avoid unnecessary interfaces, base classes, factories, wrappers, and generic abstractions.
- Don't create an interface merely because a class exists.
- Prefer simple constructor injection where dependency injection is useful.
- Keep dependencies explicit.
- Avoid excessive layering, indirection, and speculative extensibility.
- Avoid unnecessary design patterns and architectural ceremony.
- Prefer cohesive code over artificially fragmented methods and types.
- Keep public APIs intentional and minimize unnecessary surface area.

## Idiomatic .NET

- Prefer standard .NET APIs and conventions over custom implementations.
- Use LINQ for clear collection transformations, but prefer ordinary loops when they are more readable or efficient.
- Avoid unnecessary allocations and repeated enumeration.
- Use async/await for asynchronous I/O and propagate asynchronous operations naturally.
- Never block on asynchronous work using `.Result` or `.Wait()`.
- Support and propagate `CancellationToken` where cancellation is meaningful.
- Prefer `Task` over `ValueTask` unless there is a demonstrated reason to use the latter.
- Use `IDisposable` and `IAsyncDisposable` appropriately for owned resources.
- Prefer `DateTimeOffset` for timestamps representing actual instants.
- Use `TimeProvider` when time-dependent behavior needs to be testable.
- Handle exceptions intentionally. Don't catch exceptions merely to log and rethrow or suppress errors.
- Don't use exceptions for ordinary control flow.

## Readability and Naming

- Use descriptive, concise names that communicate intent.
- Follow conventional C# naming and formatting rules.
- Prefer guard clauses to deeply nested conditionals.
- Keep control flow easy to follow.
- Use expression-bodied members when they improve readability.
- Avoid dense expressions, excessive method chaining, and nested ternaries.
- Prefer code that explains itself over comments describing implementation mechanics.
- Write comments to explain intent, constraints, or non-obvious decisions.
- Avoid unnecessary regions, decorative comments, and redundant documentation.

## Performance

- Avoid obvious inefficiencies without prematurely optimizing.
- Consider allocation patterns, algorithmic complexity, and I/O behavior.
- Avoid materializing collections unnecessarily.
- Avoid repeated database queries, accidental N+1 operations, and excessive enumeration.
- Use spans, pooling, low-level APIs, and specialized collections only when justified.
- Don't sacrifice clarity for speculative micro-optimizations.
- Measure performance-sensitive behavior before introducing significant complexity.

## Testing and Correctness

- Design code to be testable without distorting production architecture.
- Test observable behavior rather than implementation details.
- Prefer focused tests with clear inputs and expected outcomes.
- Avoid excessive mocking and brittle interaction-based tests.
- Cover important edge cases, failure modes, and boundary conditions.
- Preserve existing behavior unless a change is explicitly required.
- Never introduce silent error handling or misleading fallback behavior.

## Agent Behavior

- Inspect the surrounding code, project configuration, and existing conventions before making changes.
- Respect `.editorconfig`, analyzers, nullable settings, and project-specific standards.
- Prefer the smallest coherent change that fully solves the problem.
- Don't introduce packages, frameworks, or architectural patterns without clear justification.
- Don't create abstractions for one-off implementations without a concrete benefit.
- Don't refactor unrelated code or introduce formatting-only changes outside the task.
- Avoid compatibility shims and legacy patterns unless actually required.
- Verify compilation and run relevant tests when tooling is available.
- Explain meaningful tradeoffs and non-obvious design decisions.
- When multiple approaches are reasonable, prefer the simplest solution that satisfies the actual requirements.
